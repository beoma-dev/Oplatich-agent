# Beoma database change

Прочитай корневые инструкции, service-checks и существующий механизм миграций.
Сначала установи движок и источник истины: PostgreSQL, SQLite, действующий ledger
либо код инициализации. Не вводи PostgreSQL/новый ledger в проект с SQLite.
При наличии `.quality/profile.json` и service-standard используй их реальные роли,
namespace тестовых баз и требования к неизменности исторических миграций.

Определи данные и версию схемы ДО изменения, потребителей старого формата,
исторические периоды, ограничения уникальности и разрешения чтения/записи.
Уже применённый SQL не переписывай: добавляй следующую миграцию/шаг согласно
проектной конвенции, supersession фиксируй отдельно. Для SQLite проверь существующий
способ обновления старого файла, а не только создание пустой базы.

На disposable PostgreSQL либо временной копии синтетического SQLite проверь:
- создание чистой схемы и обновление предыдущей поддерживаемой версии;
- сохранение исторической атрибуции/дат и ожидаемых totals, отсутствие потери строк;
- реальные grants/ограничения, прямой обход API и недопустимые значения;
- повторный запуск там, где механизм обещает идемпотентность; ledger не дублируется;
- сбой в середине шага и состояние транзакции/ledger после него;
- размер блокировок/время на репрезентативной синтетической нагрузке, если меняется
  большая таблица или порядок чтения/записи.
Не превращай нерелевантные пункты в формальные тесты. Дай причину неприменимости.

Не направляй fixtures в production. Не считай имя test_database достаточной
изоляцией: сверяй сервер/DSN и namespace ДО destructive DDL; при доступном
проектном `./check` используй его свежий Docker-контейнер. Не печатай DSN/дампы
с секретами. Не запускай автоматически миграции на живом сервисе для проверки.

До разрешённого применения подготовь точные SHA/SQL, совместимость старого и
нового кода, ограничения окна, проверку backup восстановлением и план возврата.
Если обратная миграция теряет новые данные, скажи это прямо: rollback кода и
восстановление данных — разные операции. Предпочти совместимый expand/contract,
если одновременное переключение потребителей не обеспечено.

Сохрани реальные команды/результаты и непройденные проверки; выполни `beoma-review`
перед main. Skill сам не разрешает production DDL, восстановление, простой или
удаление данных. При сбое применения останови следующий шаг, проверь фактическое
состояние и используй только заранее разрешённый план; не повторяй destructive
команды вслепую ради зелёного результата.
