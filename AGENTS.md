# AGENTS.md — инструкции для AI-агентов

## Что это

Telegram-бот подачи заявок на оплату счетов. Два канала ввода — форма Mini App
(страница `webapp/` + API `api/`) и пошаговая чат-форма (`bot/handlers.py`);
оба сходятся в `services/intake.py::finalize_submission`. Бот называется
**Оплатыч**, его марка — `webapp/logo.svg` (отдаётся статикой из `webapp/`,
используется в шапке формы, favicon и пустых списках). `logo.svg` —
единственный источник геометрии персонажа: производные знаки в
`assets/brand/` ЦЕЛИКОМ генерируются из него командой `npm run brand`
(`scripts/render_brand.mjs`) — `avatar-512` (фото бота, BotFather →
`/setuserpic`), `mark-512` (прозрачный фон, на любую подложку),
`mark-neutral-512` (без тона — ч/б печать, чужой бланк, золотистая
подложка), `cover-640x360` и `cover-540x360` (обложка Mini App, BotFather →
`/newapp`; жёсткий размер у него 640×360, второй файл собирается под ручной
запрос этого размера). Ни SVG, ни PNG в `assets/brand/` руками не правим: правим
`logo.svg` и пересобираем, иначе набор разъезжается с маркой (уже было).
Фон аватарки почти БЕЛЫЙ с розовым подмесом: она живёт рядом с чужими
цветами — темами Telegram и акцентом темы пользователя, — и насыщенный
круг с ними спорит, а почти ахроматичному спорить нечем. Обод — не
украшение, а единственный край: на светлой теме круг без него растворяется
в подложке; цвет обода повторяет кепку, поэтому меняете кепку — меняйте
и обод в скрипте. Обложка, наоборот, НАСЫЩЕННО розовая: она лежит внутри
своей карточки приложения, спорить ей не с чем, — но подложка под знаком там
темнее фона, а не светлее, иначе розовая кепка на светлом углу держится на
одной обводке. Кегль заголовка обложки подбирается замером ширины, а не
константой: у 540×360 текстовое поле на 16% уже, и константа вылезала за край.
Тёмный вариант фона аватарки сохранён в комментарии там же:
он контрастнее на 40 px, но глуше по бренду. Масштаб не
константа: скрипт замеряет фактический радиус марки и вписывает её в
безопасный круг, потому что Telegram обрезает фото по вписанной окружности,
а квадрат и непрозрачный фон обязательны — прозрачное станет чёрным. Mini App разложен по
файлам: `index.html` — только разметка, `app.css` — стили (модальное окно — в `modal.css`, живая инструкция —
в `tour.css`; оба подключаются ПОСЛЕ и заканчивают каскад), `app.js` — логика
(один IIFE), `form-lib.js` — чистые функции формы, `skin-field.js` — фон, панели
(`*-panel.js`), `list-tools.js` и `help-tour.js` — вынесенное из `app.js`.
Стили экранов, добавленных позже, — `modal.css`, `tour.css`, `stats.css`.
Стили экранов, что подключаются ПОСЛЕ `app.css`: `modal.css`, `tour.css`,
`stats.css`.
Порядок подключения значим: `modal.css` идёт ПОСЛЕ `app.css`,
`form-lib.js` и `skin-field.js` — ПЕРЕД `app.js`, а ранний выбор темы остаётся инлайном в `<head>` (иначе неон мигнёт
светлой темой до отрисовки). Краткое описание
архитектуры по пунктам ТЗ и стоимость реализации — в
[ARCHITECTURE.md](ARCHITECTURE.md), полное описание решений и их причин — в
[CONTEXT.md](CONTEXT.md), деплой — в [DEPLOY.md](DEPLOY.md). Срезы состояния
проекта (качество, безопасность, эксплуатация) и их незакрытые риски — в
[reports/](reports/); правила ведения — в [reports/README.md](reports/README.md).

## Команды

```bash
# Запуск (нужен .env с TELEGRAM_BOT_TOKEN; пустой WEBAPP_URL = без API/HTTPS)
python main.py

# Линт
ruff check .

# Пересборка фирменных знаков из webapp/logo.svg (нужен Chromium, см. ниже)
npm run brand

# Тесты (токен подставит tests/conftest.py, внешний не нужен)
pytest -q
node --test tests/js/

# Браузерные проверки Mini App (нужен npm ci и Chromium)
npm ci && npx playwright install chromium
npm run test:e2e

# Очистка тестовых данных перед прод-запуском: отчёт «что будет удалено»
python scripts/purge_data.py                  # только отчёт, ничего не удаляет
python scripts/purge_data.py --preset all --apply --yes   # удалить (со страховочным бэкапом)

# Смоук-проверка импортов (без реального токена)
TELEGRAM_BOT_TOKEN=dummy:token python -c "import main, api.server, bot.handlers, services.intake"
```

## Конвенции

- Python 3.11+: типы PEP 604 (`X | None`), `zoneinfo`, async/await.
- Комментарии, докстринги и все тексты для пользователя — **на русском**.
- Синхронный I/O (файлы) — только через `asyncio.to_thread`, не блокировать
  event loop.
- Любая пользовательская строка перед отправкой с `parse_mode=HTML` — через
  `html.escape`.
- В логи не попадают суммы, реквизиты, содержимое файлов и токены.

## Инварианты — менять синхронно, не ломать

- **Дополнительные документы** (`extra_files`) — необязательный список,
  до `MAX_EXTRA_FILES` штук, те же формат и размер, что у счёта. Живёт во
  ВСЕХ каналах: `webapp` (поле в основном блоке), чат-форма (шаг
  `EXTRA_DOCS` между счётом/реквизитами и подтверждением), `api/routes`
  (поле формы `extra_files`), колонка «Дополнительные документы» в конце
  реестра. Предел числа файлов зеркалится в JS — стережёт
  `tests/test_webapp_sync.py::test_extra_files_limit_mirror`.
- **Счёт и реквизиты — НЕОБЯЗАТЕЛЬНЫ** (с 26.08.2026). Заявка принимается
  и без того, и без другого: бывает «оплатить по договору, документы будут
  позже», а требование «одно из двух» заставляло вписывать выдуманные
  реквизиты. `has_invoice` в модели отражает ФАКТ (файл приложен), а не
  выбор в форме, иначе карточка обещала бы финансисту вложение, которого
  нет. Пустую заявку карточка называет прямо: «Ни счёта, ни реквизитов».
- **Закрывающие документы** (`closing_files`, колонка «Закрывающие
  документы») дописываются в УЖЕ существующую строку реестра: акт и УПД
  приходят после оплаты, иногда через месяц. Ручка `/api/my/closing-docs`
  принимает их только от АВТОРА заявки или админа, дописывает к тому, что
  уже приложено (документы носят частями), и сообщает финансистам отдельным
  сообщением — карточка к тому времени давно уехала вверх по переписке.
  Правка одной колонки существующей заявки — через
  `storage.set_request_field`, а не новым `set_status`-подобным методом
  в каждом бэкенде.
  Кнопка подписана «📄 Акт / УПД», а не «Закрывающие»: слово канцелярское,
  а в ряду из трёх кнопок на 360 px каждый лишний символ виден. Полная
  формулировка — в подсказке кнопки. Показывается кнопка только у
  ОПЛАЧЕННОЙ заявки (или там, где документы уже приложены): до оплаты акта
  не бывает, а место в ряду не бесконечное.
- **Напоминание о просрочке подаёт АВТОР** (`/api/my/nudge`,
  `webapp/nudge-panel.js`) и это не дубль планировщика: тот шлёт сводку по
  всем просроченным разом, в назначенный час и с оглядкой на личные
  настройки получателя, — а здесь человек просит про свой конкретный
  платёж, поэтому сообщение идёт ВСЕМ получателям и мимо настроек
  напоминаний. «Просрочена» проверяется на сервере (`_is_overdue`):
  признак вычисляемый, и верить присланному приложением нельзя. Повтор по
  одной заявке — не чаще `NUDGE_INTERVAL_SECONDS` (6 часов); отметка живёт
  в SQLite (`request_meta.claim_nudge`), а не в памяти процесса, иначе
  деплой открывал бы окно заново. Не доставили никому — отметка СНИМАЕТСЯ
  (`forget_nudge`), иначе человек шесть часов считал бы, что напомнил.
- **Ряд действий в «Моих заявках» — максимум ТРИ кнопки**: на экране в
  360 px под него остаётся 294 px, и три кнопки прежнего кегля (324 px)
  уезжали на вторую строку. Отсюда меньший кегль именно у `.my-actions
  .add-btn` и главное действие заливкой (`add-btn` без `btn-ghost`), а
  админское «удалить любую» переехало в подробности заявки
  (`showRequestDetail`): четвёртая кнопка ломала строку, а рядом с
  «Отозвать» две красные читались как одно и то же. В ряду удаление
  осталось только у СВОЕЙ отозванной заявки. То же и в панели финансиста:
  у новой заявки там три кнопки статуса, и удаление было четвёртым.
  `makeTappable` третьим аргументом получает перезагрузку списка — она же
  признак «удаление показывать в окне». Добавляете кнопку — меряйте
  `tests/e2e/lists.test.cjs`: там проверка на один ряд и на долю ширины.
- **Под карточкой в чате ОДНА кнопка — «Открыть в приложении»**
  (`notifier.build_card_keyboard`). «Оплачено / Отложить / Отклонить» из
  чата убраны с 27.08.2026: те же кнопки видны в панели сразу, вместе со
  счётом и историей, а в чате они удваивали высоту карточки и позволяли
  переставить статус случайным касанием в ленте. ДВА исключения, оба
  обязательные: если открыть приложение нечем (`WEBAPP_URL` пуст, а в
  группе ещё и короткое имя Mini App), кнопки статуса остаются — карточка
  обязана давать способ действовать; и `bot/finance_actions.py` остаётся
  на месте, потому что кнопки на УЖЕ разосланных карточках живут в
  переписке месяцами и нажатие на них не должно упираться в тишину.
- **Кнопка «Открыть в приложении» зависит от ПОЛУЧАТЕЛЯ**
  (`notifier.open_button`): в личку — `web_app` с `?fin=<id>`, в группу —
  прямая ссылка `?startapp=fin_<id>`, потому что `web_app`-кнопки Telegram
  в группах не разрешает. Отличаем по знаку `chat_id` (у людей он
  положительный). Клавиатура поэтому строится ВНУТРИ цикла по получателям,
  а `cards.update_all` принимает не готовую клавиатуру, а функцию от
  `chat_id`. Прямая ссылка требует ЗАРЕГИСТРИРОВАННОГО в BotFather
  короткого имени: если `MINIAPP_SHORT_NAME` разойдётся с тем, что выдал
  BotFather, ссылка молча ведёт в никуда — Telegram на такое не ругается,
  кнопка просто не работает. Почему не работала ПЕРВАЯ версия кнопки, так
  и осталось невыясненным (имя на стенде оказалось верным); web_app в личке
  снял вопрос вместе с самой зависимостью от имени. Приложение ловит и
  `start_param` из initData, и `?fin=` в адресе. Права всё равно за
  сервером: не финансист получит отказ выборки.
- **Что бывает после `fin_`** (разбирает `webapp/list-tools.js`): номер
  заявки — в ПОИСК панели; `overdue` — фильтр «⚠️ Просрочены»;
  `due_<с>_<по>` (ISO-даты) — окно плановых дат. Своих выборок под это не
  заводим: у панели ровно эти фильтры уже есть, они подставляются В ПОЛЯ
  (иначе непонятно, почему список короткий) и снимаются «Сбросить».
  Разделитель — подчёркивание: в `startapp` Telegram пропускает только
  буквы, цифры, `_` и `-`. Список НОМЕРОВ в ссылку не кладём: сводка
  собрана в свой час, а открывают её позже — «просроченные на сейчас»
  честнее вчерашнего перечня, и он не упрётся в 512 символов.
- **`start_param` — не всегда чат возврата**: там же ходят `help` и
  `fin_<id>`. В `return_chat` уходит ТОЛЬКО число (`/^-?\d+$/`), иначе
  экран уезжает туда, где сервер ждёт chat_id, и отбраковывает его.
- **Валидация зеркалится в трёх местах**: `bot/validators.py` (сервер),
  `webapp/index.html` (JS-зеркало: CURRENCIES, ARTICLES, лимиты длин, форматы
  файлов, парсинг суммы/даты), `api/routes.py` (использует серверные
  валидаторы). Меняешь поле формы — правишь все три + `bot/models.py`.
- **Реестр и файлы — только через `services/storage.py`** (фасад: local =
  SQLite + xlsx-зеркало, google = Sheets + xlsx-зеркало); модули
  `google_backend`/`registry_sqlite`/`registry_xlsx` напрямую из хендлеров
  не дёргать. Первые девять колонок `SHEET_HEADERS` — ровно по ТЗ, порядок
  не менять. CSV упразднён.
- **Лист реестра в Google-книге пришпилен по gid** (`GOOGLE_SHEET_GID`,
  по умолчанию 0), и КАЖДЫЙ диапазон адресуется по имени листа через
  `google_backend._rng()`. Безымянный диапазон («A1», «1:1») Google относит
  к ПЕРВОМУ листу книги: пока лист был один, это сходило с рук, а рядом со
  «Справочником» достаточно перетащить вкладку, чтобы заявки поехали
  в соседнюю таблицу. Нет листа с нужным gid — `_target_sheet()` ОТКАЗЫВАЕТ,
  а не берёт первый: тихая запись не туда всплывёт через месяц при сверке,
  а отказ поднимет критичный алерт `storage`. Инвариант стережёт
  `tests/test_google_mock.py::test_every_range_names_the_registry_sheet`.
- Порядок колонок реестра: `SHEET_HEADERS` ↔ `InvoiceRequest.as_sheet_row()`
  (bot/models.py) — единый источник, менять парой. Новые колонки только
  ДОПИСЫВАТЬ в конец: вставка в середину сдвигает уже заполненные реестры
  (Sheets, xlsx, SQLite) — старые строки уезжают на колонку влево. Новое поле
  в SQLite-реестре требует ещё и записи в `_FIELDS` (services/registry_sqlite.py):
  колонку в уже существующей таблице досоздаёт `_add_missing_columns`,
  потому что `CREATE TABLE IF NOT EXISTS` готовую таблицу не трогает.
- `POST /api/invoice` защищён подписью Telegram initData (`api/auth.py`).
  Новые маршруты, принимающие данные пользователя, обязаны проверять подпись
  так же. Маршруты «своих» данных (`/api/my-requests`, `/api/my/withdraw`)
  берут автора ТОЛЬКО из проверенного initData — никогда из тела запроса.
  `/api/finance/*` показывает чужие заявки — доступ через
  `_may_see_requests()` (финансист ИЛИ админ) или `is_bot_admin()`, отказ пишется в аудит.
- **Состав финансистов, whitelist и админов — только через
  `services/runtime_settings.py`**: `effective_*_ids()` = запись из `.env`
  плюс добавленные из панели, минус отозванные (`*_off`). Читать
  `settings.admin_ids`/`allowed_user_ids` напрямую там, где решается «есть ли
  право», нельзя — назначенный из панели админ окажется бесправным.
  Исключение по замыслу: у админов нет списка отключённых — запись из
  `ADMIN_IDS` панелью не снимается, владелец сервера остаётся владельцем.
- **Запрос доступа — один сервис `services/access_requests.py`**: и кнопка
  в чате, и `/api/access/request` зовут `request_access`, решение админа —
  `resolve_access`. Ручки `/api/access*` проверяют подпись initData, но НЕ
  whitelist: они существуют ровно для того, у кого доступа ещё нет.
- **Напоминания настраивает получатель**: `rs.personal_reminders(id)` = общие
  настройки как значения по умолчанию плюс личные поверх. Планировщик тикает
  раз в полминуты и смотрит, кому сейчас его время; `run_reminders` — ручной
  прогон, он обходит общий выключатель, но НЕ личный отказ (`muted`).
- **Смена статуса — только через `services/status_change.apply_status`**:
  им пользуются и кнопки карточки в чате, и панель Mini App; иначе каналы
  разъедутся в поведении (карточки, причина, аудит, уведомление автору).
- **Статусы заявки зеркалятся**: `bot/models.py` (`REQUEST_STATUSES`,
  `STATUS_NEW`, `STATUS_WITHDRAWN`), `bot/my_requests.py` (`_STATUS_ICONS`),
  `webapp/index.html` (`STATUS_ICON`, `STATUS_CLASS`, `STATUS_ACTIONS`) +
  раскраска в
  `registry_xlsx.py` и `google_backend._style_requests`. Анти-дрейф стережёт
  `tests/test_webapp_sync.py::test_statuses_mirror`.
- **Настройки раздаются по трём уровням, и уровень виден в разметке**
  (`webapp/index.html`): `data-admin` — только админам («Доступ»,
  «Здоровье», карточка бэкапа), `data-recipient` — получателям, то есть
  финансистам и админам («Напоминания», «Данные»), без атрибута — всем
  («Оформление», «Бета»). Вкладок шесть, и в одну строку они помещаются
  впритык: добавляете седьмую или удлиняете подпись — меряйте
  `tests/e2e/settings.test.cjs`, там проверка с запасом по всем
  контрольным ширинам.
  Элемент с `data-admin` ОБЯЗАН иметь `hidden` и в разметке: `applyAdmin`
  при старте ничего не переключает (значение не изменилось), и без этого
  карточка мелькнёт у того, кому не положена. Ссылки на реестр финансист
  получает отдельной ручкой `/api/registry/links`, а не через
  `/admin/settings`: полная админ-панель ему не положена.
- **Бета переключается на двух уровнях**: `rs.autofill_enabled()` — общий
  выключатель админа, он главнее; `rs.personal_autofill(id)` — личный выбор
  поверх него. Разбор счёта спрашивает ЛИЧНЫЙ (`api/routes.py`), иначе
  отключивший себе распознавание всё равно его получит.
- **Осмысленность текста — два разных инструмента, не путать**
  (`bot/validators.py`): `looks_broken` ОТКАЗЫВАЕТ и потому содержит только
  безошибочные правила (нет ни одной буквы, один символ шесть раз подряд);
  `looks_like_gibberish` и `has_profanity` только ПРЕДУПРЕЖДАЮТ — эвристики
  ошибаются, а сорванная оплата дороже кривой строки. Мат ищется по корням,
  но засчитывается лишь в начале слова или после приставки: подстрокой «еб»
  сидит в «потребности», «муд» — в «мудром». Подтверждение подозрительного
  текста идёт отдельным флагом `confirm_text`, НЕ общим `force`: иначе оно
  заодно снимало бы проверку на дубль.
- **Своя сторона не может быть контрагентом**: автозаполнение сверяет
  кандидата с `ORG_INN` (ИНН наших юрлиц и ИП) и пропускает совпавшего.
  Без этого списка отличить нашу сторону от чужой нечем: в счёте она стоит
  рядом и выглядит так же («ИП с ФИО»), а PDF-слой вдобавок путает колонки
  и ставит метку поставщика к строке покупателя. Заводите новое юрлицо —
  дописывайте его ИНН, иначе счёта от него начнут молча отбраковываться.
- **Настройки в памяти процесса и с диска НЕ перечитываются**
  (`runtime_settings._cache` грузится один раз): правка `bot_settings.json`
  снаружи — руками или из соседнего `docker exec python` — до живого бота
  не доходит, а первым же его сохранением затирается. Менять состав
  финансистов, whitelist и прочее надо ЧЕРЕЗ ЕГО API (`/api/admin/*`) или
  перезапуском. Ловилось живьём: отключение получателя из соседнего
  процесса выглядело успешным, а бот продолжал слать всем троим.
- **Стенд не должен уметь навредить боевому контуру**: он описан в отдельном
  `docker-compose.stage.yml` (боевые команды его не читают), сайт подключается
  файлом в `deploy/conf.d/`, данные лежат в `data-stage/`, у контейнера
  `restart: unless-stopped` (как у боевого) и `cpus: "1.0"` из двух ядер.
  Было `on-failure:5`: оно не поднимает контейнер после перезагрузки хоста —
  при штатном выключении контейнеры выходят с кодом 0, а такие `on-failure`
  не трогает. `unless-stopped` при этом уважает `docker stop`, так что
  выключить стенд на время по-прежнему можно. Прокси у стенда СВОЙ
  (`warp-stage`): с общим нельзя было отрепетировать правку прокси —
  пересоздание роняло оба контура разом, и 25.08.2026 это стоило двух
  боевых простоев. Стенд надо ПЕРЕСОБИРАТЬ отдельно: боевой
  `docker compose up -d --build` его не трогает, и он тихо отстаёт. `ENV_LABEL` рисует плашку над
  формой — без неё два бота неразличимы. `scripts/smoke_stage.py` отказывается
  запускаться при пустом `ENV_LABEL`: это его защита от боевого.
- **Уведомления о сбоях идут через `services/alerts.alert_admins(kind=...)`**:
  категория из `rs.ALERT_KINDS` сверяется с настройками панели, но критичная
  (`CRITICAL_ALERT_KEYS`, сейчас потеря заявки) не выключается ничем — ни
  тумблером категории, ни режимом «только критичные». Новый вид алерта
  ОБЯЗАН получить `kind`: без него он подчиняется только главному режиму, и
  выключить его по отдельности будет нечем. Журнал инцидентов
  (`rs.record_incident`) ведётся ВСЕГДА, даже по выключенным категориям и по
  задавленным троттлингом повторам: выключен звонок, а не датчик, — иначе
  панель врала бы о том, что сбоев не было.
- **На google-бэкенде зеркало xlsx НАДО включать руками** (`REGISTRY_XLSX_FILE`),
  иначе реестр существует в одном экземпляре — в таблице. Пока переменная
  пуста, `storage.registry_export_path()` отдаёт None: зеркало не пишется,
  `/export` пустой, а `registry_check` отвечает «зеркало не настроено» и
  `ok: True` — то есть страж молчит именно тогда, когда сторожить нечего.
  Ловилось живьём 01.09.2026: в бэкапе лежал файл девятидневной давности
  с двумя строками при восьми в реестре. Проверка бэкапа берёт имя файла
  ИЗ НАСТРОЕК, а не «registry.xlsx»: прибитое имя читало старый файл и
  рапортовало об успехе. Документы (счета, PDF) на этом бэкенде живут
  в Drive и в архив НЕ попадают — `verify_backup` говорит об этом прямо.
- **Зеркало xlsx может разойтись с реестром, и это проверяется**
  (`services/registry_check.py`): истина в SQLite или Google-таблице, но
  финансисты открывают файл, а его запись намеренно вторична — сбой пишется
  в лог и не отменяет заявку. Сверка идёт по «ID заявки», показывается в
  карточке «Здоровье бота» и уходит алертом категории `mirror` после
  каждого бэкапа. Выключен бэкап — остаётся только панель.
- **Права на команды бота в чате держит `bot/admin.py::_admin_gate`**, и он
  покрыт тестами (`tests/test_admin_commands.py`) — раньше подмена его на
  «пускать всех» не роняла ни одного из 494 тестов, хотя за ним лежат
  `/export`, `/backup`, `/audit` и `/allow`. Тесты проверяют не только ответ
  функции, но и последствия: посторонний не получает файл и не меняет списки.
- **О пропаже связи бот сообщает почти всегда задним числом**: пока
  Telegram недоступен, сообщение об этом уйти не может тем же каналом.
  `services/health.probe_once` шлёт одну попытку на провал (повторять
  бессмысленно, а журнал забился бы счётчиком) и полноценное сообщение —
  при восстановлении, с длительностью. Живое состояние видно в карточке
  «Здоровье бота»: Mini App отдаётся с нашего домена и открывается тогда,
  когда сообщения не доходят.
- **Аналитика считается на СЕРВЕРЕ** (`services/analytics.build` — чистая
  функция, `/api/admin/analytics`, экран `webapp/stats-panel.js`). Доля или
  медиана, посчитанная в приложении, — это вторая копия метрики, и она
  разойдётся; панель только раскладывает присланные числа. Суммы НИКОГДА
  не складываются между валютами. Просрочка берётся из
  `reminders.split_by_deadline`, а не считается заново — третьей копии
  правила «что такое просрочено» быть не должно. Время «подача → оплата»
  есть ТОЛЬКО в аудите (`audit.paid_times` разбирает строку
  `«INV-… → Оплачена»`, которую пишет `status_change`): в реестре момента
  смены статуса нет. Меняете формат той строки — метрика молча обнулится,
  стережёт `tests/test_analytics.py`.
- **Права админа приходят в `/api/access`, отдельной пробы нет**: приложение
  раньше дёргало `/admin/settings`, чтобы понять, показывать ли админские
  вкладки, и получало 403 — журнал безопасности забивался обычными
  открытиями формы (147 записей из 200 за неделю на боевом). Заводить такую
  пробу заново нельзя: `ADMIN_DENIED` должен означать попытку, а не заход.
- **ФИО в реестре — из справочника, а не из профиля Telegram**
  (`services/staff.py`): профиль человек меняет когда захочет, и в отчёте
  вместо «Микула Татьяна» оказывается «Танечка». Порядок разрешения —
  `staff.resolve`: справочник → `EMPLOYEE_NAMES` из `.env` → имя профиля;
  пусто не бывает никогда, и справочник НЕ мешает подаче (сбой чтения
  логируется, заявка проходит). Зовут его ОБА канала подачи.
  Справочник живёт в нашей SQLite и является источником правды; Google-
  таблица (`STAFF_SHEET_ID`) — только источник импорта по кнопке админа,
  при подаче заявки бот в Google не ходит. Импорт СЛИВАЕТ: добавляет и
  обновляет, но не удаляет — увольнение это решение человека, а не разница
  двух списков; кого в таблице нет, показываем списком. Ключ записи —
  аккаунт: тот же `@username` с другим ФИО значит «переименовали», а не
  «их двое». Числовой id подставляется САМ при первой заявке
  (`learn_id_sync`) и дальше главнее ника: ник сменить можно, id нет.
  Нулевые и отрицательные id не хранятся и не ищутся — иначе такой id
  совпадал бы с любым незнакомцем и выдавал чужое ФИО (ловили живьём).
  Числовой id ставится не только при подаче: `link_known_sync` при каждом
  открытии карточки подтягивает известные боту id по нику, иначе после
  импорта справочник считал «не подавал» и того, у кого заявки есть.
  «Подавал заявки» берётся из АУДИТА (`audit.submitters`), а не из наличия
  id. Закрывающие документы и напоминания о просрочке получили СВОИ события
  (`CLOSING_DOCS`, `OVERDUE_NUDGE`): раньше они писались как
  `REQUEST_SUBMITTED`, и приложивший акт считался подавшим заявку; в старых
  записях они отличаются только формой `details` — у подачи там « · ».
  Заявки, поданные ДО появления справочника, подписаны именем из профиля;
  `staff.backfill_registry` (кнопка «✍️ Обновить ФИО в реестре») переписывает
  в них только ФИО в скобках и только для аккаунтов из справочника.
- **Адреса файлов Mini App версионируются по содержимому**
  (`api/server.asset_version`, `index_html`): страницу отдаёт свой маршрут
  и дописывает `?v=<hash>` к своим `.js/.css/.svg`, ссылку на telegram.org
  не трогает. Заголовок `no-cache` этого не заменяет: он обязывает
  переспросить сервер, но WebView Telegram держит страницу живой и после
  деплоя показывал старый JS — ловили живьём, человек считал, что правку
  не выкатили. Версия считается по СОДЕРЖИМОМУ: пересборка без правок
  оставляет адреса прежними, и кэш продолжает работать. Добавляете файл
  в `webapp/` — ничего делать не надо, он попадёт в отпечаток сам.
- **Аналитика — отдельный экран и ТОЛЬКО админу** (`services/analytics.py`,
  `/api/admin/analytics`, `webapp/stats-panel.js`): на одном экране суммы,
  контрагенты и загрузка всей компании, поэтому право то же, что у
  админ-панели, и отказ так же пишется в аудит. Считает ВСЁ сервер —
  `analytics.build` чистая функция от строк реестра, отметок об оплате и
  справочника; доли и медианы в JS не пересчитывать, иначе метрика заживёт
  в двух местах. Суммы НИКОГДА не складываются между валютами. Время
  «подача → оплата» есть только в аудите (`audit.paid_times` разбирает
  `details` события `STATUS_CHANGED`) — меняете формат строки в
  `status_change`, поправьте разбор: стережёт `tests/test_analytics.py`.
  Экран, а не вкладка настроек: вкладок там шесть и в строку они влезают
  впритык. Иконок в шапке стало пять — предел, на который рассчитан
  `layoutHeaderIcons` (класс `icons-5` ужимает марку).
- **Права админа приложение узнаёт из `/api/access`**, отдельной пробы нет.
  Была: приложение дёргало `/admin/settings`, ловило 403 и писало отказ
  в аудит КАЖДОМУ не-админу — 147 записей из 200 на боевом за неделю,
  журнал «кто пытался» переставал отвечать на свой вопрос.
- **Живая инструкция за флагом `ANIMATED_HELP`** (`webapp/help-tour.js`,
  `tour.css`): пять анимированных шагов над текстовым экраном, формат
  «сторис» — полоски, тап вперёд, удержание паузит. Текст ПОД ней остаётся
  всегда: тур — быстрый обзор, а справочник нужен и после него (и его
  сверяют при изменениях). Автопереход завязан на `animationend` полоски,
  а не на таймер, иначе пауза расходится с показом. Разметка сцен —
  строки в самом файле, данных пользователя в них нет, поэтому innerHTML
  там безопасен; появится подстановка — переводить на textContent.
  Подключается тур САМ, наблюдая за `#help-view`: app.js у потолка. При
  системном «уменьшить движение» не строится вовсе. Флаг едет в
  `/api/access`; на боевом он выключен, обкатка идёт на стенде.
- **Бета-функции гасятся одним тумблером** и не меняют основной сценарий:
  автозаполнение (`services/invoice_extract`) только ПРЕДЛАГАЕТ значения,
  подстановку делает пользователь, и заполняются лишь пустые поля.
- **Тесты не ходят в Google**: `tests/conftest.py` принудительно ставит
  `STORAGE_BACKEND=local` и гасит `GOOGLE_*`. Не убирать: репозиторий бывает
  развёрнут на сервере рядом с боевым `.env`, и без этого `pytest -q` пишет
  тестовые заявки в настоящий реестр.
- Переменные окружения документируются в `.env.example` (единственный
  справочник) и читаются только через `config.py`.
- Относительные пути (`STORAGE_DIR` и т.п.) разрешаются от каталога проекта
  через свойства `config.Settings`, не от CWD.

## Не трогать

- `.env`, `secrets/` — секреты; `data/`, `storage/` — рабочие данные
  (реестр заявок, файлы счетов, справочник пользователей).
- Не коммитить и не логировать содержимое этих каталогов.

## Перед коммитом

1. `ruff check .`
2. `pytest -q` и `node --test tests/js/`.
3. Смоук-импорт (команда выше).
4. Трогал стили или раскладку Mini App — гонять `npm run test:e2e`: каскад CSS
   и раскладку из исходника не видно, тесты по тексту их не ловят.
5. Если менялись поля заявки — проверить все четыре точки: чат-форма,
   `webapp/index.html` + `webapp/app.js`, `api/routes.py`, `bot/models.py`.
